# Deployment

`helm/greenroute` is the application release and `kubernetes/namespace.yaml` is the GitOps bootstrap for a dedicated Pod Security `restricted` namespace, quota and limits. PostgreSQL, Redis, ingress/certificates, identity, secret management and the observability operator/backends are platform dependencies and should have independent lifecycle, backup and access ownership.

The reference quota covers the production HPA maxima plus one rolling-update surge per workload and the migration Job. Recalculate that envelope whenever replicas, HPA maxima or container requests/limits change; a lower platform quota must be paired with lower release values rather than allowing HPA scale-up to fail at runtime.

Apply the namespace bootstrap out of band with a platform-administrator identity, provision `greenroute-runtime` from the secret manager, then render/lint/schema-check the environment values before install. The release identity is intentionally namespace-scoped and cannot create or weaken the namespace, Pod Security labels, quota or limits.

Production deployment is performed by the protected release workflow with `--atomic`, signed multi-architecture manifest digests and an exact chart/config revision. The four product images and pinned OAuth2 Proxy wrapper are all built/attested, scanned, SBOMed and keyless-signed by the release. The workflow does not accept a static kubeconfig. Configure the Kubernetes API or its authentication gateway to trust `https://token.actions.githubusercontent.com` for the dedicated `KUBE_OIDC_AUDIENCE`, map the `sub` claim to the username, and bind only `repo:<owner>/<repository>:environment:<stage|prod>` subjects to the namespace deploy Role. Store `KUBE_API_SERVER`, base64-encoded public `KUBE_CA_CERT_DATA` and `KUBE_OIDC_AUDIENCE` as protected environment variables. The workflow obtains a fresh short-lived token through a Kubernetes exec credential and verifies that the authenticated username contains the exact repository and protected environment before any mutation.

Before Helm mutates the release, the workflow verifies the pre-provisioned namespace controls and secret key names, renders the exact digest-based manifests, asserts the internal/authentication call graph, and submits every resource through server-side dry-run. This invokes cluster schema validation and admission policies against the same release inputs.

Protected stage/production environments must also define the real HTTPS `OIDC_ISSUER_URL`, `OIDC_CLIENT_ID`, explicit `OIDC_ALLOWED_EMAIL_DOMAIN`, public host/API URL, narrowed ingress-controller `TRUSTED_PROXY_CIDRS`, and separate comma-delimited `DATABASE_CIDRS`/`REDIS_CIDRS`. Register `https://<PUBLIC_HOST>/oauth2/callback` at the IdP. The runtime Secret must include independent OAuth client/cookie secrets in addition to datastore, internal-service, audit/abuse and provider credentials; values are never read or printed by the workflow.

External Compose images use `version@sha256:manifest-list-digest`. The manifest-list digest is architecture-neutral and was resolved from the named release; a single-platform mirror will have a different child/config digest. Application image digests cannot exist before the release build, so `values.yaml` records a non-`latest` application version and the release workflow injects the pushed/signed digest. Admission policy should reject mutable or unsigned production references.

Do not use the local Compose PostgreSQL/Redis or local-only credentials for a shared environment. Do not scale `routing-orchestrator` beyond one replica while provider-derived state storage remains forbidden; see the chart README and ADR-005.
